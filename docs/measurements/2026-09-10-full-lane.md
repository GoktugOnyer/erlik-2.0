# The whole lane against the lab — 2026-09-10

Every runnable case, both lab targets, re-measured after a week of adding
detection. Lab only: DVWA, Juice Shop and containers started on this machine.
Nothing outside it was contacted, and no client environment has been assessed.

The headline is not the finding count. **The lane changed the target's admin
password while declaring `state_changing: false`**, and it reported a hardened
application as clean when in fact 156 of its 208 probes received no bytes at
all. Both are fixed, and both were found only by running it.

## Four defects, none of which a fixture would have found

### 1. The lane changed the target's admin password

DVWA's csrf module changes the password on a bare **GET**: its handler runs on
`isset($_GET['Change'])` and compares `password_new` with `password_conf`. With
neither present both are NULL, `NULL == NULL`, and the password becomes
`md5("")`. Measured:

    GET     /vulnerabilities/csrf/?Change=Change                  -> password changed
    HEAD    /vulnerabilities/csrf/?Change=Change                  -> password changed
    OPTIONS /vulnerabilities/csrf/?Change=Change                  -> password changed
    GET     /vulnerabilities/csrf/?Change=Change&password_new=x    -> no change
    GET     /vulnerabilities/csrf/                                -> no change

`form_endpoint` builds that URL deliberately — the 2026-09-09 work added it
because `?id=<payload>` alone never reaches DVWA's handler and
`?id=<payload>&Submit=Submit` does. Baking the submit control into the URL is
what made the lane's only true positives possible, and it is also what made the
URL an **action rather than a page**. The scope gate never saw it, because the
gate treats GET, HEAD and OPTIONS as inherently safe.

It took three separate paths to close, found in that order because each one hid
the next:

1. **The crawler fetched it.** Every discovered endpoint was handed to katana as
   a seed, form-synthesised URLs included, so katana visited
   `?Change=Change` as a page. This was the original path and the last one
   found — its request is not a catalogue step, so searching the step outputs
   for `Password Changed.` showed nothing.
2. **Per-URL cases fetched it.** CONF-06, CLNT-07, CLNT-07b, SESS-02, INFO-03
   and INPV-07 read a URL rather than probing a parameter on it. On a form URL
   that is all cost and no benefit.
3. **One step ignored the parameter it was given.** WSTG-CLNT-04's
   `common_parameter_sweep` appends six guessed redirect names — `redirect`,
   `next`, `url`, `returnUrl`, `dest`, `continue` — and none of the form's own,
   so it submitted the form blank. Its five sibling steps all carry
   `{{parameter}}` and are harmless: the hazard is the shape, not the case.

Verified after the fixes: the same run, same 9 findings, and the admin hash is
still `md5("password")`. **The guards cost nothing.**

### 2. A case that received nothing was reported as clean

curl exits 0 on an empty body. DVWA at `security=impossible` puts a **single-use**
`user_token` in its forms; `form_endpoint` baked it into the discovered URL as a
companion field, and it was stale by the time the cases ran. Measured on the
hardened arm: **156 of 208 injection-case steps received zero bytes** — every
probe of `sqli`, `sqli_blind`, `xss_r` and `csrf` — and the stage reported
`completed` with no findings.

That zero then read as "the hardened application is clean", which is the one
thing it cannot mean. The catalogue adapter now reports a case whose every
executed step came back empty, and the hardened arm re-run says so itself:

    status: partial — one or more catalogue checks never reached their target
    30 x test_case_unreachable, naming each (case, url, parameter)

One step with bytes is enough to say the target answered; all of them empty
means it did not.

### 3. Every finding cited the whole stage's evidence

`record()` unioned the stage's evidence ids onto every finding. Correct for a
scanner, whose findings arrive citing nothing and have only the stage report to
point at — destructive for the catalogue, which attaches exactly one id: the run
that produced the finding. All nine DVWA findings came out citing the **same 772
ids**, so a client could not tell which of 772 captured responses proved a given
HIGH-severity SQL injection. A finding that already cites its own evidence now
keeps only that. Before: 30 ids, the first of which did not contain the matched
text. After: 1 id, 3290 bytes, containing it.

### 4. Two redaction layers, two different rules

`orchestrator.credentials.scrub` had always skipped values under four
characters. `orchestrator.integrations.security.redact` had no guard at all — so
the DVWA identity's `security=low` cookie stored the application's own
robots.txt as `Disal[REDACTED]: /`. Stored evidence no longer matched the bytes
received. The guards are now the same length in both layers.

Separately, the runner scrubbed each step's output **as it arrived**, so the
evaluators read the redacted text. A credential is removed by substring
replacement, so an identity whose secret value was `error`, `near`, `syntax` or
`SQL` silently turned every real SQL injection into a clean result. Redaction now
happens once, over everything that leaves `run_test_case`, after the evaluators
have read what the application actually sent. **Detection must not depend on
redaction.**

## Two more the audit found

**The one finding that survived both arms was mis-titled.** `WSTG-INFO-03`
reported "robots.txt Discloses Paths" on DVWA, whose robots.txt is
`User-agent: *` / `Disallow: /` — a rule covering the whole site, disclosing no
path at all. The evaluator fired on `^User-agent:`, the one line every robots.txt
has. It now requires a path with something after the slash, so Juice Shop's
`Disallow: /ftp` still reports and DVWA's does not.

**The export carries no evidence for any finding, and that is still open.**
`IntegrationFinding` has an `evidence_ids` list and no evidence field, and the
DefectDojo payload sets `description = finding["basis"]` and nothing else. So the
byte-level proof the blind evaluators construct — the control byte counts, the
`first difference:` window quoting `User ID is MISSING` against `User ID exists`
— exists in the runner's result, is stored in the evidence blob, and never
reaches the report or the export. A client reading a HIGH-severity finding gets
one sentence of basis and a list of ids. Fixing defect 3 above made those ids
point at the right response; making the proof itself travel is the next piece of
work, and it is not done.

## A claim I got wrong, and the control that replaces it

I first reported the two DVWA arms as a clean differential: 9 findings at `low`,
1 at `impossible`, "same session, same 8 parameters, same 12 cases". That is
wrong, and an adversarial audit caught it.

The arms share **1 of 8** `(url, parameter)` pairs. At `impossible` DVWA's forms
carry a `user_token`, which `form_endpoint` bakes into the URL — so the URLs are
different strings, and "8 parameters in both arms" was a count collision rather
than the same surface. Combined with defect 2, the hardened arm never tested the
injection points at all.

The control the claim needs is one variable, so it has to be run by hand: the
same 8 pairs discovered at `low`, driven through the real runner twice in **one
session**, changing only the `security` cookie.

| case | endpoint | parameter | low | impossible |
|---|---|---|---|---|
| WSTG-INPV-05.2 | sqli | id | 1 | 0 |
| WSTG-INPV-05.2 | brute | username | 1 | 0 |
| WSTG-INPV-05.3 | sqli | id | 1 | 0 |
| WSTG-INPV-05.3 | sqli_blind | id | 1 | 0 |
| WSTG-INPV-05.4 | sqli | id | 1 | 0 |
| WSTG-INPV-05.4 | sqli_blind | id | 1 | 0 |
| WSTG-INPV-11.2 | sqli | id | 1 | 0 |
| WSTG-INPV-11.2 | brute | username | 1 | 0 |

**8 findings to 0, and zero empty responses on either side** — so both arms
reached the application and every finding tracks the vulnerability rather than
the target. That is the differential this lab exists to provide. The lane's own
two arms cannot provide it until discovery stops putting a single-use token in
the URL it reports.

## The binding constraint is discovery, and it is measurable

Juice Shop: 136 endpoints, **4 parameters**, 2 findings — both informational
(`robots.txt`, `security.txt`). Yet Juice Shop has a reachable error-based SQL
injection:

    GET /rest/products/search?q=erlik'probe
      -> HTTP 500
      -> <title>Error: SQLITE_ERROR: near &quot;probe&quot;: syntax error</title>

Handed that endpoint as its crawl root, the lane reports it HIGH in **21
seconds**. So detection works and discovery does not reach it. `/rest/products`
and `/search` were both discovered; `/rest/products/search` was not, because the
call is an Angular XHR rather than a link — and the string `products/search?q`
is sitting in `main.js`, a file the lane fetched and recorded as an endpoint.
The parameter is one JS-body extractor away from being in the inventory.

DVWA's 8 parameters are its real GET-form surface (`sqli`, `sqli_blind`,
`brute`, `csrf`, `fi`, `xss_r`), so there the constraint is coverage instead:
20 of 32 catalogue cases cannot run here. `WSTG-AUTHZ-01` covers DVWA's genuine
LFI on `fi?page` and every one of its steps needs a non-curl tool;
`WSTG-INPV-01` covers the genuine XSS on `xss_r?name` and two of its steps are
refused for carrying their own credentials, which is a fixable case defect
rather than a lane limit. Both are **untested coverage, not clean results**.

## The default budget loses two thirds of the findings

With all 12 cases selected and the default `max_urls=120`, DVWA yields **3
findings in 83s** instead of 9 in 245s. `target_budget` gives each case
`(120 // 12) // steps` targets — 1 for an 11-step case — and all 12 emitted a
truncation notice, so the lane is honest about it. But the six lost findings are
every SQL injection on `sqli` and `sqli_blind`, and which parameters survive is
decided by sort order: `brute?username` comes before `sqli?id` alphabetically,
so the arbitrary half is what got tested.

## Zeros that are correct, and how it is known

`brute?password` and the two `csrf` password fields were probed by every SQL case
and reported nothing; DVWA does not concatenate those into a query at `low`.
`WSTG-SESS-02` reported nothing on 35 URLs: DVWA sets `HttpOnly; SameSite=Strict`
on both cookies. The 93 blocked requests on DVWA and 14 on Juice Shop were all
`host outside scope` — off-site links the applications publish — and no allowed
request reached a host outside the declared scope.

## What this run does not establish

- **Nothing about a client environment.** Two deliberately vulnerable lab apps.
- **No POST, JSON, path, header or cookie parameter** was tested; the lane probes
  GET query parameters only.
- **Juice Shop has no security-level control**, so its zeros rest on hand checks
  rather than a differential.
- **The hardened arm remains untested coverage** until discovery stops baking a
  single-use token into the URL. The lane now says so; it does not yet fix it.
